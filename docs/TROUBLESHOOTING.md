# 排障手册（Troubleshooting）

> 结合诊断报告（`sessions/diagnostics`）与日志使用。诊断报告已脱敏：用户 ID 哈希、密钥/密码/系统提示词移除、超长字段截断。

## 一、如何获取诊断信息

1. 控制台 → 群会话 → 目标副本 → 「诊断」导出脱敏诊断报告；
2. 打开调试日志（配置 `advanced.debug = true`）后复现问题；
3. 需要保留原始模型载荷时开启 `advanced.store_model_payloads`（会增大数据库，排查后请关闭）。

## 二、常见故障

### 1. 指令没反应 / 文本未送达

- **现象**：`/酒馆 xxx` 无响应，或主动通知没有到达。
- **原因**：
  - QQ 官方接口吞 `/`（`all_as_at` 时序）；已内置 `_parse_command_relaxed` 兜底，但若适配器前缀配置冲突仍会失效；
  - 平台不支持主动私聊、目标平台实例已经下线，或统一消息来源失效；
  - 群不在白名单、发送者非管理员。
- **处理**：核对平台适配器命令前缀 → 核对 `admin_ids` / `allowed_group_ids` → 在 WebUI 待办查看最后错误并重试。

### 2. 主动消息被拒（频控 40034100）

- **原因**：QQ 官方接口对主动消息有频控；同一轮过多提醒会被整段拒绝并重试刷屏。
- **处理**：插件已内置「计时器单循环 + 去重 + 失败退避」；仍可降低 `time_rules` 中各类提醒频率，或关闭 `announce_timeouts`。

### 3. 投票结束后不推进

- **原因**：定时器驱动的投票结束可能不携带「表决通过 → 推进叙事」的触发（历史缺陷，v0.11.3 已修复为按实票判定并标记 `pending_resolution`）。
- **处理**：升级到 v0.11.3+；仍不推进时发送任意一条剧情消息触发 `pending_resolution` 自动续写。

### 4. 检定骰面与叙事不一致

- **原因**：表决路径曾丢弃 `lock_check_result` 返回值，模型失败重试会用新骰面（v0.12.0 已修复为复用凭证骰面）。
- **处理**：升级到 v0.12.0；回放与展示应始终一致。

### 5. Windows 下临时目录 / 备份清理失败（WinError 32）

- **原因**：SQLite 连接在操作结束后短暂滞留会锁住文件。插件刻意采用「每操作新建连接、退出即关闭」，这是承重设计（v0.12.0 曾评估连接池后因该原因回退）。
- **处理**：重试清理；不要在插件运行中直接删除 `data_dir`；备份用控制台「备份导出」。

### 6. 建卡码过期 / 无法绑定

- **原因**：默认 1800 秒过期；跨设备绑定依赖平台消息 ID 稳定。
- **处理**：调整 `time_rules.card_code_ttl_seconds`；过期会自动补发（`-1` 表示不限时，v0.11.1 已修复不限时建卡码不被误标过期）。

### 7. 世界包导入冲突（409）

- **原因**：同 slug 已存在且内容版本相同，但内容不同。
- **处理**：控制台弹窗三选一（覆盖为新修订 / 另存副本 / 取消）；`worlds/migration` 可先对比冻结契约差异。

### 8. 章节里程碑一直不触发 / 章节长期不切（2026-09-20）

- **现象**：剧情早已兑现当前章的 `exits_when.all_milestones`，但 `story_ledger`
  里始终没有对应的 completed 行，`progress.completed_milestones` 不再增长，
  当前章卡住几十个回合。
- **原因**：叙事模型写的 `kind=milestone` 账目会被 `engine._validated_ledger_ops`
  一律丢弃（设计如此），里程碑只能由模型裁判 `_judge_chapter_milestones` 落账；
  而该裁判的输出上限原为 `min(config.max_tokens, 800)`。待判定里程碑一多，
  JSON 被 max_tokens 截断 → 解析失败 → 原实现静默 `continue`，判定整批丢失。
  线上 `re0-ch-chapter030` 第 5 章「王选散场」因此在 40 个回合里 0 次落账，
  最近 24 次 `milestone_judge` 调用中 22 次 `output_tokens` 正好等于上限。
- **自查**：`token_usage` 里 `request_type='milestone_judge'` 的 `output_tokens`
  是否密集贴着上限；`audit_logs` 中 `actor_id='milestone_judge_refresh'` 说明
  裁判确实在跑（跑了但没有判定）。
- **处理**：裁判改用独立宽松上限（`_milestone_judge_max_tokens`，≥2400）、
  `temperature=0`；输出被截断时抢救数组里已完整的里程碑条目并记 warning；
  提示词要求 `quote` 只取 8—40 字、`reason` ≤40 字，从源头压缩输出。

### 9. 信息获取太慢（打听很多轮，里程碑不动）

- **现象**：玩家一轮轮打听，每轮只拿到一层线索，来源明明知道全部答案却
  留到下一轮；一个来源不知道时也不给下一跳，只能逐个登门试。线上
  `re0-ch-chapter030` 第 6 章「同盟的筹码」24 个回合只达成 1/3 条里程碑，
  裁判每次都给出「仅计划备案，未实际发出预警」「未提及白鲸威胁，无同盟
  安排或行动」。
- **原因**：两层错位。①叙事层挤牙膏，没有任何规则要求「一次打听给全」；
  ②里程碑层错位——`m_06_02_warning_sent`、`m_06_03_alliance_ready` 判定
  的是「某件事已经发生」，叙事却一直把它当成「再多给一条线索」，而
  节奏指令 HARD 分支原本还写着「完成对应目标、公示所需抉择**或给出关键
  线索**」，等于给了模型一个永远可以退回去的出口。
- **自查**：`audit_logs.action='milestone.judge'` 的 `verdicts.*.reason`
  是否反复出现「仅计划/仅提议/未实际」；`story_ledger` 里 pending 里程碑
  的 `title`（即判定条件原文）用的是「已实际发出/执行」还是「获知」。
- **处理**：`prompts._information_delivery_rules()` 落成硬规则（一次给全、
  给结论不给猜谜、来源不知道就当场给下一跳、禁止多跳链、已知不重复、
  同场共享、要价不跨轮）；`milestone_requirement_kind()` 把达成条件粗分为
  `info` / `action`，节奏指令给每条 pending 打上〔需信息〕/〔需行动〕，
  并在 HARD 时要求「至少一条〔需行动〕里程碑的判定条件全部凑齐，只给线索
  不算推进」；选项层要求「需行动」章节至少两个选项是现在就能做出来的
  动作，四选项全是打听时由 `_maybe_force_decisive` 强制重生成。
- **注意**：分类只影响指令措辞，**不参与任何达成判定**；里程碑仍然只由
  证据裁判落账。

## 三、日志关键标记

| 标记 | 含义 |
|---|---|
| `notification_outbox` / 投递失败 | 主动文本已进入可靠通知补偿流程 |
| `AI 酒馆 <stage>.<op> 失败（transient/integrity/policy/unknown）` | v0.12.0 统一失败上报（`tavern/errors.py`） |
| `AI 酒馆计时器轮询异常，将在稍后重试` | 定时器循环自愈 |

## 四、数据库维护

- 数据库：`data_dir/catalog_v090.sqlite3`（Schema 10），WAL 模式；
- 自动备份：迁移前自动生成 `catalog_v090.schema{旧}.before_schema{新}.*.sqlite3`；
- 完整备份：控制台「备份导出」（ZIP，含数据库与独立存档目录）。
