# 世界包作者实践指南（Best Practices）

> 生成入口见 [世界包生成提示词](../worlds/WORLD_GENERATOR_PROMPT.md)，字段落点见 [编写说明](WORLD_AUTHORING.md)，协议见 [WORLD_SCHEMA_V5.md](WORLD_SCHEMA_V5.md)。本文负责正反例、内容演练与发布验收，适用于所有题材，不要求每个本都采用反转、悲剧或分头调查。

## 一、基本准则

1. **世界包只是声明式数据，不是任意代码**。使用当前协议支持的条件和操作，不加入脚本、可执行表达式或想象中的自动修复字段。MD 是创作规范，必要文字规则要进入实际世界包，机械保障要有实现依据。
2. **先设计可玩场景，再补设定和 JSON**。回答玩家为什么参与、能争取什么、选择怎样改变局面、何时结束。格式与可玩性都要验收，不能以 `inspect_world_package` 或 `tests/test_v0110.py` 的严格体检通过代替叙事演练。
3. **版本纪律**：
   - `world_schema_version`：协议结构版本（2/3/4/5），改动结构时递增；
   - `world_content_version`：内容版本（如 `3.0.0`），内容迭代时递增；
   - 控制台导入时按「内容版本新旧」判断覆盖或拒绝；同 slug 同版本但内容不同会触发冲突弹窗，不要静默覆盖。

## 二、常见陷阱

| 陷阱 | 表现 | 对策 |
|---|---|---|
| 属性 ID 与角色卡标签不一致 | 检定报「属性不属于世界或角色卡」 | 保证 `attributes[].key` 与角色卡 `stats.labels` 完全一致 |
| 属性让玩家自由分点或临场生成 | 职业定位与实际数值脱节，建卡繁琐 | 写包模型按职业预设数值，插件自动计算，关闭任意手动改值，保留主副属性选择与原有面板 |
| 职业太少或只有名称不同 | 玩家选择受限、玩法同质 | 职业建议至少 6 个，通常 6–8 个，有实际定位和属性差异；不足时说明理由 |
| 背景、性格、秘密分别要求自由填写 | 建卡像交作文，玩家迟迟无法开演 | 必要短标识外以少量预设选择为主，只留一个可选补充说明，允许跳过 |
| 检定 DC 超出难度区间 | 检定被夹取 | 用 `default_difficulty` 与 `difficulty_min/max` 约束范围内取值 |
| 全队行动选项超量 | 被自动降级为个人选项 | 每轮全队行动 ≤ `MAX_TEAM_CHOICES=2` |
| 开场场景过长 | 首回合上下文膨胀 | 开场控制在一屏内，细节交给 `initial_state` 的 facts |
| 生僻名词堆叠 | 玩家知道气氛，却看不出眼前是什么 | 常见名称在前，专名在后；首次出现时补外形、位置或用途 |
| 用古建术语代替空间描写 | 玩家分不清门、台子、走廊和城墙部件 | 先写物体类别与空间关系，再补风格名；每个场景明确出口、障碍和可互动物 |
| `preset_stack` 叠加顺序混乱 | 属性计算与预期不符 | `preset_stack` 始终基于 base 属性重算，保持确定性顺序 |
| 交互规则互相矛盾 | dry-run 命中冲突 | 用控制台 `worlds/simulate` 逐步试运行并查看裁定凭证 |
| 把“节奏紧凑”写成逐回合反转和加罚 | 每次成功后又出危险，没有获得感 | 保留成果，允许舒缓；新事件须有因果，不凑固定节拍 |
| 把五人逐个表演、至少一人失败写成里程碑 | 人数不足、全员成功或拒绝动作时卡关 | 验收成果，写替代办法与真实前置；不预设玩家失败 |
| 多人指令标成个人选项 | 玩家被擅自移动，或选菜单也被权限拦截 | 先核对行动范围，再标记个人/现场小队/全队；不靠自动降级绕授权 |
| 新线索只换名称和载体 | 日记、残页、口供反复讲同一件事 | 每条说明信息增量、独立验证价值或新行动用途，否则合并 |
| 任何矛盾都用幻觉解释 | 调查无法排除假说，玩家不再信任结果 | 先固定真实因果，限定感知欺骗范围，给出可验证支点 |
| 读写 NPC 章节状态当成写背景 | 已救出的人下一章又在险地 | 核查 `key_npcs[].state` 的实际写入，避免覆盖可变成果 |
| 短章省略最短体验门槛 | 预算很短但引擎仍要求继续停留 | 显式核对 `min_turns`，与 `max_turns`、人数和总行动量一起计算 |
| 所有谜团和个人后日谈都必须完成 | 主线已结束仍逐人补任务 | 核心冲突收束后一次尾声，可选内容不进入退出门槛 |

## 三、协议 v5 五层引擎速记

`Entity Registry → Condition → Operation → Event Pipeline → Resolution Receipt`

- 实体注册表：NPC、能力、物品的先验定义；
- 条件引擎：谁在什么情况下可以做什么；
- 操作引擎：规则裁定后的机械结果（扣血、给物、改状态）；
- 事件管线：开馆、回合、检定、表决等事件如何串行推进；
- 裁定凭证：每次机械裁定幂等落库，可回放、可审计。

## 四、陌生题材的白话化测试

发布前把开场和任意三个章节场景交给一个不了解设定的人，只让其回答四个问题：

1. 人物现在位于室内、室外、地下还是高处？
2. 最近的门、窗、台阶、平台、通道或障碍在哪里？
3. 本段新出现的名词分别是什么东西，有什么作用？
4. 玩家下一步能观察、接近、绕过、使用或攻击什么？

再追加两个可玩性问题：“你为什么愿意继续？”“刚获得的信息能帮助你作什么决定？”能看懂场景不等于想玩；如果只能复述设定名词，仍需补人物目标、机会或行动用途，而不是再增加一段定义。

若读者只能复述“很仙”“很古老”“像教堂”却答不出具体物体和位置，说明描写仍然过于晦涩。修订时不要继续添加形容词，而要补充常见物体名称、相对位置、尺寸感和用途。

不同题材的处理方式相同：

- 修仙：“护山大阵”首次出现时说明它是罩住山门、阻挡外人进入的一层发光屏障。
- 西幻：“飞扶壁”首次出现时说明它是从教堂外墙斜撑出去、用来托住高墙的石架。
- 中世纪：“瓮城”首次出现时说明它是两道城门之间用于困住闯入者的封闭空地。

专名可以保留风味，但专名不能成为理解剧情的门槛。

## 五、可玩性正反例

以下“反例”指将某种桥段写成通用硬要求，不表示禁止题材使用该桥段。真正不可替代的剧情前提要有因果、人数/能力匹配和失败分支，不能只说“作者要求”。

| 问题 | 不推荐 | 推荐 |
|---|---|---|
| 设定教学代替目标 | 本章讲清三个仪式术语，每回合解释一个 | 玩家要找到阻止仪式的方法；只解释当前选择需要的规则，教义留待追问 |
| NPC 只作线索容器 | 每次追问都咳嗽，反复说“不要相信……” | 一次说清可执行信息，或说明恢复后能回答什么；另有欲望和主动行动 |
| 固定人数与失败门槛 | 五人分别入幻，至少一人失败才能切章 | 队伍取得识别干扰的方法；物证、实验或可靠证词任选，允许累计 |
| 伪装成个人的集体指令 | `collective: false`，文本“让甲守门，乙随我走” | 个人选项只写自己行动；多人分工通过实际支持的授权流程确认 |
| 成功不算数 | 斩断连接成功，下轮连接无解释恢复并继续吸血 | 连接已断成为事实；若敌人尝试重建，须有新行动、依据和响应机会 |
| 失败等于重来 | 开锁失败，再给同一开锁选项，无任何变化 | 明确噪声、耗时或工具损失，允许换办法、绕行或撤退；不保证总能成功 |
| 反转无限改答案 | 每章必须推翻已知事实，所有证据都可能是假 | 真相先确定，错觉有边界；反转有证据，可靠验证后保留结论 |
| 治疗只是暂时描写 | 治好伤口但无新原因立刻恢复同一 debuff | 普通状态按治疗规则解除；剧情锁定事先声明原因与解除路径，或不可解除性质及风险 |
| 世界时间服从分镜 | 无论是否解除警报，第六回合追兵必到 | 写追兵动因和警报条件；玩家成功解除警报后改变该事件 |
| 终章交作业 | 必须逐人说感想、讲完所有知识点才结束 | 最终决定落实后一次交代核心后果，个人后日谈可选 |

### 示例：调查场景的最小设计稿

- 玩家目标：找出仍可通行的撤离路线，带走被困者。
- 人物与阻力：看守想等失踪亲人回来，不愿交出钥匙；旧桥状况不明。
- 关键成果：取得一条实际可用的路线及进入办法，不要求玩家拿到指定钥匙。
- 可行方式：交涉取得钥匙、勘察另一条通道、修复旧桥；具体风险按世界实际能力结算，不保证每条路成功。
- 信息增量：地图提供另一入口，现场勘察验证能否通行；二者不是重复朗读地名。
- 同行/分头：同行更便于保护，分头可扩大调查覆盖；不论采用哪种方案，成果按实际证据累计，消息通过交流传递。
- 失败与恢复：方法失败后兑现对应后果，考虑换路、耗资源、撤退或失败终局；如使用资源，填入实际消耗、恢复数值及可达条件。
- 提前解决：玩家提前修好桥，后续承接撤离，不再要求回去取得钥匙。
- 场景结束：路线实际可用，且相关选择和当前行动已结算；“计划修桥”或只读到“桥”字不算完成。

这是一份内容设计稿，不是可直接导入的协议对象。生成时映射到目标版本支持的字段；不要照抄为新增 `alternate_paths`、`auto_repair` 等未核对字段。

## 六、交付验收矩阵

每次新写或实质改写世界包，按适用项目演练。对不适用项给出题材/机制理由；不能只走一条作者理想路线。静态体检检查结构，机械模拟检查实际规则操作，叙事桌面演练检查因果与可玩性，三者不能互相冒充。

| 场景 | 具体输入或扰动 | 通过标准 |
|---|---|---|
| 正常主线 | 从开场按一条合理路线走到结局 | 看得懂、愿意介入，线索有用途，选择有后果，核心冲突能结束 |
| 职业预设建卡 | 遍历所有职业，跳过自由补充，并返回更换职业 | 属性由预设自动生成且修正正确，换职业不叠加旧值；职业建议至少 6 个或说明不足理由，保留主副属性固定加点和基础/加成/最终值/修正面板，无任意手动改值或额外自由作文项 |
| 最低人数/缺职业/缺席 | 使用允许开局的最低人数，不选择作者偏爱的职业；再考虑中途缺席 | 有可行承接或明确的暂停/退场规则，不擅自操控缺席者，不要求不存在的人完成动作 |
| 拒绝分头 | 玩家全程同行或选择另一种分组 | 不因未演出指定分镜卡章，不临时拆队，不无因提高移动难度 |
| 全员成功 | 应检定行动均得到成功结果 | 不为完成章节强塞失败、入幻、受伤；成果能够积累并推进 |
| 连续失败 | 关键路线连续检定失败 | 兑现损失，存在换方法、撤退或失败终局，不把失败改成成功或无限原地重试 |
| 重复调查 | 对同一对象重复同一方法，又询问一个真正的新问题 | 已知信息简述，不制造假新线索；新问题按其实际价值回答 |
| 分队权限/知情 | 甲请求移动乙；远处小队取得一条线索 | 未获授权不移动乙；角色不自动知道远处发现，不假定群聊支持秘密投递 |
| 提前取得成果 | 提前营救 NPC、取得道具或断开危险连接，再切入原定相关章节 | 后章承接新事实，NPC 状态和局势不无因重置，不要求重演 |
| 成功与恢复 | 普通状态治疗成功、代价成功、合理休息分别演练 | 纯成功不追加惩罚，代价成功保留成果，恢复按规则兑现；新状态须有新来源 |
| 剧情锁定与资源 | 选一个剧情锁定状态，并核算全部必需动作和恢复机会 | 锁定有原因与解除路径，或已声明不可解除及风险；数值可执行，恢复本局可达，不存在未声明的全队连坐 |
| 公平悬疑 | 玩家用设计中的验证方法排除一个假说 | 验证按范围生效，关键结论不被随口推翻；矛盾不能自动解释成幻觉 |
| 漏记与误记 | 一份已完成事件记录漏记；另给只含计划/关键词或矛盾的记录 | 仅按实际证据补记，计划/提及不算完成，不能超期补剧情。未有运行支持时记为未验证并说明限制 |
| 节奏预算 | 核算各章 `min_turns`、`max_turns` 与个人/团队行动、表决、尾声 | 不靠填充消息满足门槛；主动角色扮演不被强行打断，时限有实际因果 |
| 最终处置 | 核心冲突已结束、最终决定已落实，但仍有可选背景和个人故事 | 完整输出尾声并结束主线，不再重复表决、逐人补任务或强加牺牲 |

### 验收记录格式与发布阻断项

每项记录：`检查方式（静态/机械模拟/叙事演练）｜字段或场景｜输入与前置事实｜预期结果｜实际结果与证据｜通过/待改/未验证/不适用｜原因`。

机械结果记录实际裁定凭证或测试输出；叙事演练记录具体过程和结论；漏记检查引用真实事件或明确标注的测试夹具，不编造运行日志。自检材料与世界 JSON 分开，按交付要求提供，不把整份报告塞进运行时提示词。

以下是**作者发布验收要求，不表示现有导入器已自动检查全部项目**：

- 必需动作在允许人数/能力下不可完成，或必须有人检定失败才能推进：待改，不能发布。
- 核心收益、资源收支、治疗/锁定规则或终局条件不清，必须依赖无限重试：待改，不能发布。
- 个人选项替全队决定、章节覆盖已获救人物等已知状态冲突：待改，不能发布。
- 关键机制依赖未实现能力，或机械模拟尚未验证：简化设计、补足验证或阻断发布，不能报通过。
- 格式通过但白话化、动机、线索用途或终局演练失败：内容返工，不能以“JSON 合法”结案。

### 既有问题包的回归用法

可用《坐忘录·山门诡事》作为审查样本，检查本规范能否指出：术语授课、默认分头、五人依次心斋且至少一人入幻、成功反噬、后章固定 NPC 位置、终章逐人交代等风险。这是对规范的内容回归，不是修改该包或当前存档的授权，也不代表这些风险已被自动检查器全部覆盖。

同一规则还应能用于其他题材，例如科幻包的技术术语、侦探包的证据公平性、战争包的分队与资源、喜剧包的舒缓结尾。不能为了修一个修真本，把所有后续世界写成同一种故事。

## 七、性能与体积上限

- 单世界包建议 ≤ 200KB，实体数量克制；过大包会拖慢体检与模拟；
- `world_simulate` 已做 JSON 深度 / 解压体积限制，勿依赖超大 payload；
- 常驻 NPC 用独立文件（`*-npcs.json`）维护，避免主世界包臃肿。

## 八、调试建议

1. **先静态体检**（`worlds/preflight`），再**模拟试运行**（`worlds/simulate`），最后**真实开馆**；
2. 用「诊断报告」（`sessions/diagnostics`）核对会话状态、事件流与裁定凭证；
3. 需要回归防护时，把世界包加入 `tests/fixtures/` 并复用 `test_v0110` 的体检断言。
4. 另外执行第六节叙事演练并保存证据。机械 dry-run 不会证明故事有吸引力，MD 检查表也不会修复运行时代码；未验证能力必须明确标注。

## 九、人物一致性与原作依据

- 重要 NPC 必须明确身份、效忠关系、价值底线、当前目标及改变立场的条件；不能仅列性格形容词或写死“下一步必须做什么”。
- 核心设定与位置、伤势、已知信息分开。历史误演不应反向污染人物身份，也不能为恢复原作而撤销玩家成果。
- 改编包按章提供经人工核对的原作片段和人物性格参考，隔离未来秘密与不同轮回；检索结果不是本局事实。
- 明确区分被提及者、可感知者、需要自主决定者。同地点不代表共享私语，分头角色不能自动知情。
- 按需决策、空间映射、调用预算和当前不支持的情形见 [NPC_DIRECTION.md](NPC_DIRECTION.md)。不能以启用该开关替代人物资料审查。
